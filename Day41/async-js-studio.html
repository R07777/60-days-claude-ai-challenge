Asynchronous JavaScript, from first principles to production patterns

JavaScript runs on a single thread, yet modern apps fetch data, animate, and respond to users without ever freezing the page. This tutorial builds the mental model that explains why — the Call Stack, the Event Loop, the Task Queues — and layers Promises and async/await on top until you can read, debug, and write asynchronous code with real confidence.

Module 1 · Foundational

The Call Stack and the Event Loop

Before Promises make any sense, you need the machine underneath them. This module builds that machine, piece by piece.

1.1 · Single-threaded, but not blocked

JavaScript engines (like V8, which powers Chrome and Node.js) execute code on exactly one Call Stack — one thread, one thing happening at a time. If JavaScript only had the Call Stack, any slow operation (reading a file, waiting for a network response, a 3-second timer) would freeze your entire page until it finished. That would make the language unusable for the web.

The trick is that the JavaScript engine doesn't work alone. It runs inside a host environment — the browser or Node.js — which provides extra machinery: Web APIs (or Node APIs), a Callback Queue, a Microtask Queue, and an Event Loop that ties it all together. Slow work is handed off to that environment, and the Call Stack stays free to keep running your code.

🍳 Analogy — The single chef

Imagine a kitchen with exactly one chef (the Call Stack) but several timers, a delivery counter, and a whiteboard of orders. When a dish needs to simmer for 20 minutes, the chef doesn't stand and stare at the pot — they set a timer (hand it to a Web API), and immediately start the next order. When the timer rings, the finished step doesn't interrupt the chef mid-chop; it gets written on the whiteboard (a queue) and the chef picks it up the moment they finish what's currently in hand. One chef, many pots simmering "at once" — that's concurrency without parallelism.

✕ Common misconception

setTimeout(fn, 0) does not run immediately. It still hands fn to the Web API layer and queues it as a macrotask — which only runs after the current script finishes and the entire Microtask Queue is empty. That's why, above, D prints after C even though the timer delay is 0.

1.4 · Callbacks and the road to callback hell

Before Promises existed, asynchronous results were delivered through callback functions — a function you pass in, to be called later when the work finishes. This works, but nesting several dependent async steps produces deeply indented, hard-to-read code.

getUser(userId, (user) => { getPosts(user.id, (posts) => { getComments(posts[0].id, (comments) => { console.log(comments); // each step only knows how to start once the previous one calls back — // error handling has to be repeated at every single level }, onError); }, onError); }, onError);

This nested shape is nicknamed the "pyramid of doom." Module 2 introduces Promises specifically to flatten this pyramid.

✓ Key takeaways
  • JavaScript executes on one Call Stack — synchronous code always runs to completion first.
  • Slow work is delegated to Web APIs, which queue their callbacks instead of blocking the stack.
  • The Microtask Queue (Promises) is always fully drained before the next Macrotask (setTimeout, events) runs.
  • Deeply nested callbacks ("callback hell") motivated the design of Promises.
Module 2 · Building

Promises

A Promise is an object representing a value that doesn't exist yet, but will — or will fail trying. It replaces "call me back" with "here's something you can attach reactions to."

2.1 · The three states

Every Promise is created in the pending state and can settle exactly once, into one of two final states:

StateMeaningTriggers
PendingNeither fulfilled nor rejected yet.Initial state on creation.
FulfilledOperation succeeded, a value is available.resolve(value) called.
RejectedOperation failed, a reason is available.reject(error) called, or a thrown error.
🎟️ Analogy — The takeout ticket

Ordering food at a counter gives you a numbered ticket, not the food itself. The ticket is pending. Eventually it becomes either "ready for pickup" (fulfilled — here's your value) or "sorry, we're out of that dish" (rejected — here's a reason). You can hand that ticket to someone else and say "let me know when this resolves" — that's exactly what .then() does.

2.2 · Creating and consuming a Promise

const orderCoffee = new Promise((resolve, reject) => { setTimeout(() => { const beansAvailable = true; if (beansAvailable) resolve('☕ latte ready'); else reject(new Error('out of beans')); }, 1000); }); orderCoffee .then(result => console.log(result)) // runs if fulfilled .catch(err => console.error(err)) // runs if rejected .finally(() => console.log('counter clear')); // always runs

2.3 · Chaining flattens the pyramid

Each .then() returns a new Promise, so chains read top to bottom instead of nesting inward:

getUser(userId) .then(user => getPosts(user.id)) .then(posts => getComments(posts[0].id)) .then(comments => console.log(comments)) .catch(err => console.error('any step failed:', err));

A single .catch() at the end catches a rejection from any earlier step in the chain — that's the main win over repeating error handlers at every callback level.

2.4 · Running several Promises together

CombinatorSettles whenUse it for
Promise.allAll fulfill, or the first one rejects (fails fast).You need every result and can't proceed with a partial set.
Promise.allSettledAll settle, regardless of outcome.You want every result and every error, none ignored.
Promise.raceThe first Promise to settle (fulfilled or rejected).Timeouts: race a fetch against a timer.

✕ Common misconception

Throwing inside a .then() does not crash your program synchronously — it turns the returned Promise into a rejected one, which the next .catch() down the chain will receive. This is what lets a single .catch() sit at the very end of a long chain and still catch errors from any step.

✓ Key takeaways
  • A Promise moves pending → fulfilled or pending → rejected, exactly once, never both.
  • .then() returns a new Promise, which is what makes chaining possible.
  • One .catch() at the end of a chain handles rejection from any earlier step.
  • Choose the combinator based on whether you need all-or-nothing (all), every outcome (allSettled), first-to-finish (race), or first success (any).
Module 3 · Applying

async / await

async/await doesn't replace Promises — it's syntax sugar built directly on top of them, letting asynchronous code read like synchronous code.

3.1 · The rules

  • Adding async before a function makes it always return a Promise — even if you return a plain value, it gets wrapped.
  • await pauses the async function (not the whole program) until the Promise it's given settles, then unwraps the value.
  • await is only legal inside an async function (or, in modern environments, at the top level of a module).
🎫 Analogy — The claim-check pause

At a dry cleaner, dropping off a coat gets you a claim check and you leave immediately — that's a callback or a bare Promise. await is different: it's like standing at the counter and simply waiting until the coat is ready before doing the next thing on your list, while every other customer at other counters keeps being served normally. Only your personal errand pauses — the whole store keeps running.

3.2 · Rewriting a chain

Promise chainasync/await
ShapeSequence of .then() callsSequence of await statements
Errors.catch() at the endtry { } catch { } wrapping
ReadabilityReads as a callback chainReads top-to-bottom like sync code
// Promise chain function loadThread(userId) { return getUser(userId) .then(user => getPosts(user.id)) .then(posts => getComments(posts[0].id)) .catch(err => { console.error(err); throw err; }); } // async/await — same behavior async function loadThread(userId) { try { const user = await getUser(userId); const posts = await getPosts(user.id); const comments = await getComments(posts[0].id); return comments; } catch (err) { console.error(err); throw err; } }

3.3 · Sequential vs. parallel awaits — a real performance trap

Each await pauses until that specific Promise settles. If three independent requests don't depend on each other, awaiting them one at a time adds their durations together instead of overlapping them.

0.0s

// Sequential — 3 × 400ms ≈ 1200ms total const a = await fetchA(); const b = await fetchB(); const c = await fetchC(); // Parallel — all start together, ≈ 400ms total const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
✕ Common misconception

array.forEach(async item => { await doWork(item) }) does not wait for each iteration before starting the next — forEach ignores the Promises returned by its callback entirely. Use a plain for...of loop with await for true sequential processing, or Promise.all(array.map(...)) for parallel processing.

Exercise · Spot the bug

This function is meant to total up prices fetched one item at a time, in order. Pick the line that breaks that guarantee.

async function totalPrices(ids) { let total = 0; ids.forEach(async (id) => { const price = await fetchPrice(id); total += price; }); return total; // ← executes before any fetchPrice() resolves }
✓ Key takeaways
  • An async function always returns a Promise, regardless of what you return inside it.
  • await pauses only the current async function, never the rest of the program.
  • Independent async calls should start together (Promise.all) rather than being awaited one after another.
  • forEach cannot be made to actually wait for async callbacks — use for...of or map + Promise.all.
Module 4 · Mastery

Microtasks, Race Conditions & Real Patterns

The last module goes underneath async/await one more time to the queue priority that governs every ordering question you'll ever debug, then applies everything to realistic problems.

4.1 · Microtasks always cut in line

After the currently running script finishes, the Event Loop does not simply alternate between the two queues. It fully drains the entire Microtask Queue — including any new microtasks scheduled while draining it — before it is allowed to take even one task from the Macrotask Queue.

setTimeout(() => console.log('macrotask'), 0); Promise.resolve().then(() => { console.log('microtask 1'); Promise.resolve().then(() => console.log('microtask 2 (queued from inside 1)')); }); // prints: microtask 1 → microtask 2 → macrotask // microtask 2 was queued *during* the drain, and still goes before setTimeout
📋 Analogy — VIP line vs. general line

The Microtask Queue is a VIP line that the host insists on fully clearing — even if someone new joins the VIP line mid-service — before calling a single name from the general line (Macrotasks). A busy Promise chain can, in principle, keep the general line waiting indefinitely.

4.2 · Race conditions in async code

A race condition happens when two asynchronous operations can finish in either order, and the code silently assumes one particular order. A classic example: a search box that fires a new request on every keystroke.

let latestQuery = ''; async function onSearchInput(query) { latestQuery = query; const results = await searchAPI(query); // BUG: if an earlier, slower request resolves after a later, faster one, // its stale results can overwrite the correct ones on screen if (query !== latestQuery) return; // ← the fix: ignore stale responses renderResults(results); }

4.3 · Debouncing an async trigger

A related, complementary fix: don't fire a request for every keystroke at all — wait until the user pauses. Debouncing delays a function call until a burst of triggers has gone quiet for a set interval, cancelling any pending call each time a new one arrives.

function debounce(fn, delay) { let timer; return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), delay); }; } const debouncedSearch = debounce(onSearchInput, 300);

4.4 · Choosing the right tool, summarized

SituationReach for
Several independent requests, need them allPromise.all
Several independent requests, tolerate partial failurePromise.allSettled
Need whichever finishes first (e.g. a timeout)Promise.race
Steps that depend on each other, in ordersequential await or a Promise chain
Stale response could overwrite a fresher onea request-id / "is this still current" guard
Trigger fires far more often than neededdebounce (or throttle)
✕ Common misconception

"async/await is faster than Promises" — it isn't; under the hood it compiles to the same microtask-based mechanics. What actually costs time is writing awaits sequentially when the operations don't depend on each other. The syntax doesn't change performance; the structure of your code does.

✓ Key takeaways
  • The Microtask Queue is drained completely — including tasks it adds to itself — before any Macrotask runs.
  • Race conditions in async UI code come from assuming responses arrive in the order requests were sent.
  • Guard against stale responses explicitly, or prevent redundant requests with debouncing.
  • async/await's readability doesn't imply extra speed — the underlying scheduling is identical to Promises.

Summary notes

Asynchronous JavaScript is one execution model wearing three outfits. Underneath everything — callbacks, Promises, async/await — the same Call Stack, Web APIs, and two queues govern what runs and when. Callbacks pass control forward but nest badly. Promises make async values into objects you can chain and combine. async/await is Promises with different clothes, valuable specifically because it lets sequential logic read sequentially, while still requiring you to think explicitly about which operations are actually independent enough to parallelize. The bugs that matter most in practice — accidental sequential awaits, forEach-with-await, stale race responses — are all consequences of forgetting this underlying model, not the syntax on top of it.
